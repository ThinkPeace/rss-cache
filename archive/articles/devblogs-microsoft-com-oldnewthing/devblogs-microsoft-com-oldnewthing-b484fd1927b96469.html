In my earlier discussion of how Windows Update uses the hot-patching space (and how nobody else should be using it), the question arose of what happens when Windows Update wants to hot-patch a binary that has already been hotpatched. Does this mean that you cannot apply hot patches two updates in a row?

Microsoft issues hot patches for two updates in a row. I linked to it in the original article, and here it is again: Hotpatch for Windows client now available.

Notice in the diagram that Windows supports two hot-patch cycles before forcing a traditional update.

The first month of each quarter issues a traditional update. Administrators who opted into the hot-patch track can install two months of hot patches, while everybody else continues to get traditional updates. At the start of the next quarter, everybody gets a traditional update again, and the cycle continues.

Okay, so how can Windows Update apply a hot-patch on top of another hot-patch?

Why can’t you tickle yourself?

Your brain knows that you’re the one doing the tickling, so it suppresses the tickle response.

And Windows Update knows that it’s patching something that it already patched, so it knows what it did to apply the hot-patch, and therefore it knows what code was originally there before it performed the hot-patch. I think all it has to do to patch a patch is update the far jump target in the trampoline to point to the new hot-patch function.

I suspect that the limit of two stacked hot-patches avoids an unbounded accumulation of internal data structures that are used to keep track of all the hot-patches, and to ensure we don’t run out of patch space in the binary itself.
