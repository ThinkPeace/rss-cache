A customer wanted their program to show a file listing with icons, and they also wanted to include an entry for the parent folder, programmatically known as .. (double period). They obtained icons by calling the SHGetFileInfo function, but they got weird, inconsistent results when they asked for the icon of the .. parent folder.

SHGetFileInfo(L"..", 0, &info, sizeof(info),
    SHGFI_ICON | SHGFI_SMALLICON | SHGFI_SYSICONINDEX);

They found that when they ran the program in a debugger, it gave them the desired folder icon 🗀. But when it ran on the customer’s system, it showed a drive icon 🖴. What’s going on? Why is the icon changing depending on who is running the program?

My psychic debugging powers¹ told me that the developer told their debugger to run the program with the current directory equal to something that is at least two directory levels away from the root. Perhaps they are using Visual Studio and accepted the default configuration that sets the current directory to $(ProjectDir), and their project directory is eomthing like C:\Users\name\repos\contoso. On the other hand, the customer is running the program while the current directory is set to an immediate subdirectory of the drive root, like C:\Contoso.

When you pass ".." to SHGetFileInfo, it is recognized as a relative path and is resolved against the current directory. And then you get the icon for whatever that turns out to be.

So what should you do if you want to get a folder icon?

You can pass the SHGFI_USE­FILE­ATTRIBUTES flag, which means, “Just pretend that I gave you a valid path to a thing with the attributes I passed as the second parameter. What icon would you use for it?”

SHGetFileInfo(L"C:\\a", FILE_ATTRIBUTE_DIRECTORY, &info, sizeof(info),
    SHGFI_USEFILEATTRIBUTES | 
    SHGFI_ICON | SHGFI_SMALLICON | SHGFI_SYSICONINDEX);

We pass a file path of C:\a and say that its attributes are FILE_ATTRIBUTE_DIRECTORY. The actual path is not important, as long as it is a syntactically valid path.
